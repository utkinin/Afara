## Обновление более старой development-копии

Перед изменениями сохранить custom-format dump и media, проверить восстановление и `AFARA_DB_PUSH=false`. Не применять начальные миграции поверх legacy schema-push базы. При необходимости только добавки analytics использовать `db:upgrade-existing` с приватным `AFARA_DB_BACKUP`. Флаг `--verify-baseline` допускает принятие истории только при точном совпадении всей схемы с независимо мигрированной `AFARA_REFERENCE_DATABASE`, имя которой заканчивается `_acceptance`. Текущая база уже проверена; повторять этот переход не требуется.

Планы содержательных добавок без записи:

```bash
npm run content:material-study
npm run content:tasks
npm run content:answers
```

Явное применение после проверки плана, с абсолютным приватным `AFARA_CONTENT_BACKUP_DIR` вне checkout (права 0700):

```bash
npm run content:material-study -- --apply
npm run content:tasks -- --apply
npm run content:answers -- --apply
```

Последняя команда создаёт только недостающие черновики. После редакционной проверки и явного решения публиковать библиотеку: `npm run content:answers -- --apply --publish-reviewed`. Публикуются только записи, точно совпадающие с проверенной библиотекой, страницей и служебными основаниями; изменённые владельцем записи пропускаются. Произвольные прежние черновики не публикуются. Повторные запуски не заменяют существующие блоки или ручные изменения.

Экспорт опубликованного содержимого выполняется отдельно по [PREVIEW.md](PREVIEW.md). Исторические архивы v1/v2 сохраняются как прежние выпуски и не заменяют текущий main или приватную CMS.
