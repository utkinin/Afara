# Применение редакционного пакета AFARA

Пакет создан 16 октября 2026 по `EDITORIAL_RESEARCH.md` и явному поручению владельца. База патча: `9243217641cf55d1ab2d50df5051458aca14f773`. Это новый пакет, а не восстановленный неизвестный архив. Результаты применения в текущей среде — в `docs/editorial-validation-2026-10-16.md`.

Выпуск v2 исправляет уникальность идентификаторов карточек между страницами. В архиве полный `afara-editorial.patch` предназначен для исходной базы выше; если уже применён первый выпуск commit `08117abcd581c9b7961aacd362fef139f118e429`, использовать вместо него `publication-fix.patch` с такой же предварительной проверкой `git apply --check`. Оба патча одновременно применять нельзя. По последующему поручению владельца коллекция опубликована: см. `docs/editorial-publication-2026-10-16.md`.

## 1. Проверить архив и изменения

Распаковать архив вне рабочего checkout. Проверить `sha256sum -c SHA256SUMS` в папке пакета. В репозитории прочитать `AGENTS.md`, проверить текущий HEAD и `git status --short`; сохранить существующие изменения, включая незарегистрированные файлы. Не сбрасывать ветку и не удалять файлы владельца.

В архиве `afara-editorial.patch` содержит код, lockfile, материалы, оптимизированные иллюстрации, манифест, тесты и инструкции. Проверить его применимость из корня AFARA:

```sh
git apply --stat /путь/к/пакету/afara-editorial.patch
git apply --check /путь/к/пакету/afara-editorial.patch
```

При конфликте остановить автоматическое применение и совместить изменения вручную, сохраняя правки владельца. Не использовать force/reset. Если пакет уже применён, повторно патч не накладывать. `git apply --reverse --check` можно использовать только как диагностику уже применённого патча; обратное применение не требуется.

После успешной проверки и просмотра:

```sh
git apply /путь/к/пакету/afara-editorial.patch
npm ci
```

В текущем AFARA код пакета уже применён; эти команды нужны при переносе на исходную или совместимую копию.

## 2. Сохранить CMS и проверить копию

Сохранить PostgreSQL в custom-format dump и отдельный архив `MEDIA_DIR` вне checkout, с приватными правами. Проверить `pg_restore --list`, затем восстановить дамп в отдельную БД с окончанием `_acceptance`, скопировать media в отдельную папку. Приложение и тесты должны использовать эту копию, не основную CMS.

Новые поля схемы не добавляются: пакет использует существующие страницы, секции, медиа и библиотеку знаний. Не запускать seed и не включать schema push. Установить `AFARA_STAGE=development`, `AFARA_DB_PUSH=false`; сохранить существующий `PAYLOAD_SECRET`, не печатать секреты. Не запускать dev и build одновременно.

```sh
npm run typecheck
npm run lint
npm run build
```

Для интеграционной приёмки запустить приложение с `DATABASE_URL` копии, её отдельным `MEDIA_DIR`, `APP_URL` и портом. `AFARA_PUBLIC_URL=https://utkinin.github.io/Afara/` включает локальный QR контактов. Затем с теми же параметрами выполнить `npm run test:editorial`. Этот тест рассчитан на **свежую восстановленную копию** до импорта; он создаёт синтетический черновик владельца, проверяет импорт и публикует материалы исключительно в тестовой БД. Для повторного полного теста нужна новая копия, а не очистка основной CMS. Обычный `npm test` тоже допускается только с изолированной `_acceptance` БД.

## 3. Подготовить черновики в существующей CMS

После проверки копии указать параметры существующей development-CMS и правильный `MEDIA_DIR`. Сначала выполнить план:

```sh
npm run content:visuals
```

Проверить список операций. Для создания черновиков:

```sh
npm run content:visuals -- --apply-drafts
```

Не выполнять эти команды одновременно из нескольких процессов. Импортёр проверяет хеши всех файлов до записи, использует транзакцию и сравнивает целиком исходные записи, существующие черновики и настройки сайта до/после. При несовпадении транзакция откатывается. Повторный запуск сохраняет уже подготовленные материалы. После неудачной загрузки могут остаться неиспользуемые производные файлы; удалять media массово нельзя.

Импорт создаёт 32 медиа-черновика, восемь неодобренных ответов и до 15 черновиков страниц. Страницы с существующим черновиком пропускаются. Существующие тексты и секции сохраняются; новый hero и коллекция предлагаются только в новом черновике. В опубликованной версии ничего не заменяется. Если нужной страницы нет, материал для неё пропускается с сообщением, пустые страницы не создаются.

## 4. Редакторская проверка и публикация

ADMIN проверяет происхождение изображений, визуальные артефакты, композицию мобильных кадров и права; затем явно подтверждает права и публикует выбранные медиа. В манифесте мобильные изображения обозначены как кадры исходных генераций, а не как дополнительные независимые работы. Коллекция не является портфолио выполненных заказов. На каждой странице с новой концепцией сохраняется объяснение коллекции; на главной оно выводится один раз для всей галереи. Старые подписи опубликованных страниц не переписываются.

После проверки страниц опубликовать их вручную. Знания проверяются отдельно: факты, внешние редакционные источники и соответствие услуге. Источники из исследования не означают независимую проверку актуальных сертификатов. Только одобренный опубликованный ответ на опубликованной странице попадёт в консультанта. Новые сообщения посетителей не становятся обучающей базой; полезный проверенный ответ добавляет редактор.

## 5. Контакты, QR, консультант и превью

Настоящий Telegram задаётся в CMS «Сайт и контакты → Подтверждённые мессенджеры». Без подтверждённого HTTPS username кнопка ведёт к внутренней форме. Контактные данные не придумываются. При отсутствии опубликованных privacy/consent приём заявок остаётся выключенным.

Для QR указать публичную HTTPS-базу в `AFARA_PUBLIC_URL` или `APP_URL`. Префикс `/Afara/` сохраняется. HTTP, localhost, IP, служебные домены и URL с credentials не принимаются. QR создаётся локально и скрыт без подходящей базы. Внешний QR-сервис не используется.

ИИ включается отдельно серверными ключом и лимитами; без ключа остаётся честно обозначенный поиск цитат. Передача вопроса в форму не создаёт заявку и не отправляет его третьим лицам. Существующее заполненное описание сохраняется.

GitHub Pages содержит только анонимно опубликованный снимок. Черновики проверяются в защищённом CMS-preview. Для обновления статического сайта использовать `PREVIEW.md`; API, заявки и консультант требуют Node-сервера. Публикация приложения не является автоматическим разрешением публиковать все подготовленные черновики.
