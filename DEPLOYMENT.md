# Переносимое размещение AFARA

Текущая проверенная машина — облачная development-среда. Реальный домен, внешний SMTP, MFA и production-хранилище ещё не подключены. Публичный запуск не выполнен. Ни домен, ни платные услуги не приобретаются этим проектом.

## Runtime

Node 24, Docker, PostgreSQL 17. `compose.yaml` **только для локальной разработки**: доверие БД ограничено loopback. Production использует отдельный `compose.production.yaml`, пароль БД, отсутствие публичного порта PostgreSQL, постоянные volumes базы и `/app/media`, процесс web и отдельный worker. Приложение в Docker работает как пользователь node. Ни файлы медиа, ни БД нельзя хранить на временном диске serverless.

Создайте защищённый `.env.production` вне системы контроля версий. Заполните `DATABASE_URL` (host `db` в compose), уникальный `PAYLOAD_SECRET`, `APP_URL=https://...`, `AFARA_STAGE=production`, `MEDIA_DIR=/app/media`, SMTP_HOST/PORT/FROM/USER/PASSWORD, ACCESS_TEAM_DOMAIN и ACCESS_AUDIENCE. БД и почтовые секреты вводятся через secret store/настройки хостинга, не чат. `POSTGRES_PASSWORD` нужен также Compose при интерполяции; используйте `--env-file .env.production`. Пароль в DATABASE_URL должен быть URL-encoded, если содержит спецсимволы. Отдельно ограничьте привилегии runtime и миграционного пользователя; compose — исходная конфигурация, не настройка минимальных прав автоматически.

Сборка: `docker build -t afara:local .`. Перед начальным запуском примените миграции внутри приватной сети: `docker compose --env-file .env.production -f compose.production.yaml run --rm web npm run db:migrate`. Предварительно поднимите db. Затем `up -d`. **Не применяйте исходную миграцию к development-базе, созданной schema push.** Проверенный путь — пустая production-база + миграции; development seed там запрещён. Первый пользователь создаётся интерактивным `npm run create:admin` в приватном контейнере. Реальные материалы заполняются отдельно через CMS.

## Вход и MFA

Payload отвечает за пароли, сессии, права и сброс пароля, но не заявляется как встроенный MFA. Выбран внешний Cloudflare Access с IdP, который требует независимый второй фактор (TOTP/WebAuthn) и персональный allowlist. `ACCESS_TEAM_DOMAIN` — точный `team.cloudflareaccess.com`; `ACCESS_AUDIENCE` — audience приложения. Приложение проверяет подпись RS256 через официальные JWKS, issuer, audience, expiry и соответствие email при входе. Неподписанный заголовок недостаточен. В production без конфигурации/валидного JWT административные запросы отвергаются даже при прямом обращении к origin. MFA-политику, recovery и защищённость каждого маршрута необходимо проверить на фактическом сервисе до запуска. Одноразовая email-ссылка не считается вторым фактором. Условия и стоимость провайдера владелец проверяет отдельно; услуги не приобретены.

У origin остаются Payload-права на каждом действии. Отключена публичная первичная регистрация, GraphQL выключен, API keys не включены. Административные cookies не хранятся в localStorage. После изменения роли сессии пользователя обнуляются. Настройте MFA также у регистратора, хостинга, GitHub, БД и почты. Recovery-коды вне репозитория. Системный шлюз не заменяет объектные ACL.

## Медиа и HTTP

Файлы хранятся в постоянном закрытом каталоге вне public; REST-выдача проверяет опубликованный статус. Загрузка сервером декодируется Sharp, нормализуется и перекодируется в WebP с удалением EXIF/GPS, создаются размеры 480/960/1600. 20 МБ, 50 MP; JPEG/PNG/WebP. Нет импорта URL, SVG и неподтверждённого HEIC. Черновики закрыты также по URL производных. Физическое удаление запрещено до проверки всех сохранённых версий. Публичные производные имеют уникальные имена, анонимные успешные ответы могут кешироваться immutable; ранее скачанный файл нельзя отозвать из чужой копии.

HTML динамический с уникальным CSP nonce, приватные ответы `no-store`; выбран поддерживаемый подход Next.js вместо сочетания кешированного HTML и повторного nonce. Нет unsafe-eval в production; unsafe-inline разрешён только для CSS из-за штатной CMS/React inline styles. Это документированное исключение. Изображения не оптимизируются повторно Next/image. Если потребуется ISR на большом трафике, нужна отдельная согласованная CSP-архитектура с измерением и проверкой опубликованного кеша. Не включайте CDN cache-everything для HTML/RSC.

TLS завершается на проверенном proxy. Приложение слушает loopback, публично доступны только HTTPS и необходимые маршруты через proxy. Настройте HSTS после проверки всех доменов; includeSubDomains/preload не включены автоматически. CSP, nosniff, Referrer-Policy и Permissions-Policy заданы приложением. Проверьте согласованность Host/Origin, тела загрузок (не менее 20 МБ в админке), заголовки proxy и ограничения времени. Непроверенные forwarded IP не используются для авторизации/лимитов.

## Заявки и worker

Одна запись leads содержит заявку и состояние outbox; успех после commit. Идемпотентность — уникальный ключ + проверка содержимого, другое обращение не блокируется по контакту. Worker каждые 5 секунд атомарно забирает задачу через `FOR UPDATE SKIP LOCKED`, держит lease 90 секунд, максимум 5 попыток, exponential backoff; SMTP ограничен 10/20 сек. Окончательная ошибка видна ADMIN. После падения lease восстанавливается. Строгая exactly-once доставка SMTP невозможна при неопределённом ответе — Message-ID стабилен, но это не обещание отсутствия дублей у получателя.

Задайте настоящего получателя в закрытой глобальной настройке Payload. Production SMTP — TLS с проверкой сертификата и авторизацией. Настройте SPF/DKIM/DMARC. Не запускайте более одного SMTP-провайдера. Rate limiter заявок хранится в PostgreSQL: общий лимит 30 за 10 минут, сохраняется после рестарта; при ошибке БД fail-closed. Это консервативный исходный лимит, требует согласования по трафику и добавления WAF/account-aware правил у gateway. Worker очищает истёкшие limiter-записи.

## Бэкап, восстановление и обновление

До размещения согласуйте сроки хранения, RPO/RTO, ответственного, расписание и отдельное защищённое хранилище. Нужна согласованная копия PostgreSQL и media (остановить правки/worker или использовать согласованный snapshot), шифрование до отправки и проверка фактического удалённого сохранения. Не хранить единственную копию на том же сервере. Ротация только внутри своего backup-префикса, последняя исправная копия не удаляется.

Локальные тесты миграции и восстановления отмечены в QA_REPORT.md. Они не доказывают внешнее резервирование production. Полная приёмка восстановления требует изолированной цели, проверки данных, версий, авторизации, медиа, реальной заявки и уведомления, а не подсчёта таблиц. SQL-ошибки должны останавливать восстановление. Перед обновлением сохранить backup, проверить зависимости/официальные advisories, прогнать типы, lint, сборку и критические тесты. Откат кода не откатывает автоматически схему БД.

При инциденте ограничить функцию/вход, сохранить технические свидетельства без текстов заявок/секретов, отозвать доступы и сессии, устранить причину, восстановить проверенную версию и проверить журнал заявок. Конкретные ответственные, мониторинг, бюджет и ограничения тарифа определяются перед запуском. Независимый аудит и испытание DDoS не проводились.

## Сборка в облаке с ограниченным DNS

В проверенной машине обычный `npm ci` на хосте работает, но BuildKit не разрешил имя proxy (`EAI_AGAIN proxy`). TLS/проверка integrity не отключались. Для сборки использован уже проверенный npm-кеш через BuildKit cache mount `afara-npm` и `--build-arg NPM_CONFIG_OFFLINE=true`. На обычном хостинге `docker build -t afara:local .` использует сеть по умолчанию. При корпоративном proxy предусмотрены необязательные BuildKit secrets `network_proxy` и `proxy_ca`; передавать их средствами Docker, не копировать ключи в исходники и слои. Публичный доверенный CA допустим как дополнительное доверие, проверка TLS остаётся включённой. Исправьте резолвинг настроенного proxy, не заменяйте его неразрешённым обходным маршрутом.

## Серверный консультант и короткие ссылки

Серверные маршруты: `POST /api/consultant` и `GET /s/[slug]`. Для них нужен тот же Node/Payload/PostgreSQL runtime, без отдельного поискового сервиса. GitHub Pages по адресу https://utkinin.github.io/Afara/ — только статический публичный снимок: в нём нет CMS, API консультанта, обработки заявок или 302. Их нельзя считать проверенными на github.io.

Консультант ищет по русскому full-text search PostgreSQL в `knowledge`, соединённой с опубликованной `pages`. Есть частичный GIN-индекс. Одновременно проверяются публикация, одобрение и актуальность источника; поиск никогда не обращается к `leads`, пользователям, личной библиотеке, внутренним файлам и версиям. Публичный текст знания показан и на странице-источнике. Обычный черновик не заменяет прежнюю опубликованную версию.

Опциональная интеграция: официальный OpenAI Responses HTTP API `/v1/responses`, модель по умолчанию `gpt-4.1-mini`. Формат `text.format=json_schema`, `store:false`, до 1100 output tokens, тайм-аут 12 секунд. Форма запроса сверена с публичным исходником официального openai-node. Реальный ключ отсутствует, сетевой вызов модели в этой приёмке не выполнялся. Выбор модели и её тариф оператор проверяет перед включением; покупки и платных запросов не было.

Серверные переменные:

- `AFARA_AI_API_KEY` — секрет, только через безопасные настройки сервера/среды, без NEXT_PUBLIC и без внесения в CMS.
- `AFARA_AI_ENABLED=true` — отдельное явное включение передачи данных; по умолчанию выключено.
- `AFARA_AI_MODEL=gpt-4.1-mini` — оператор может выбрать совместимую модель с Structured Outputs.
- `AFARA_AI_DAILY_LIMIT=100` — общая суточная квота всех запросов к консультанту; верхний предел кода 1000. Дополнительно действует общий предел 20 запросов в минуту. Счётчики в PostgreSQL, отказ при недоступной БД, очистка по expiry.

Разрешённый исходящий HTTPS-домен модели — только `api.openai.com`. Перед включением согласуйте внешнюю передачу вопроса и найденных публичных фрагментов, политику провайдера и документы обработки данных. `store:false` не является обещанием полного отсутствия любых технических журналов провайдера. Наш обработчик не сохраняет вопросы и не записывает их текст в лог, не создаёт заявки, отклоняет явный телефон/email перед передачей модели. На уровне хостинга также не логируйте тела запросов.

Без флага/ключа возвращается ближайший найденный утверждённый текст, обозначенный как поиск без генерации ИИ. При включённой модели она выбирает только ID и буквальные цитаты; сервер проверяет схему, источник и каждую цитату, сам строит внутреннюю ссылку и повторно проверяет актуальные публикации после ответа. Несогласованные версии ответа с одинаковым ключом темы блокируют ответ. Это снижает риск вымышленных фактов, но не доказывает полноту ответа, отсутствие семантической ошибки подбора или обнаружение противоречий между разными темами. Нужны регулярные редакционные проверки.

Короткие ссылки хранятся в PostgreSQL. У включённой записи обязательна опубликованная цель, имя ограничено латиницей/цифрами/дефисом. HTTP 302 имеет `Cache-Control: private, no-store`; после отключения, снятия цели с публикации или удаления — 404. Удаление цели не удаляет имя ссылки: назначение можно задать повторно. Никаких внешних URL или произвольного server-side fetch в этом механизме нет. ADMIN управляет записями, EDITOR и анонимы не читают их API.

## Новые миграции и сохранность данных

Добавлены `20261015_124033_public_content_and_consultant` и `20261015_130330_withdrawn_shortlink_targets`. Они расширяют схему, не очищают страницы, медиа, заявки и пользователей. Существующие опубликованные направления получают только метаданные подтверждённой услуги; содержательные поля не меняются. Проверены последовательное применение на пустой отдельной БД и обновление рабочей development-копии с исходным содержанием.

Используйте `AFARA_DB_PUSH=false` с сохранёнными данными и применяйте проверенные миграции явно. Не запускайте исходные миграции поверх старой schema-push базы без согласованного baseline. Локальная среда этого проекта уже обновлена; не повторяйте bootstrap поверх неё. `scripts/cloud-install.sh` применяет начальные миграции только при отсутствии таблицы pages и больше не вызывает seed. На совершенно новой development-базе демоданные можно создать отдельно явной `seed:dev`; production наполняется настоящими данными/переносом CMS.

Перед обновлением сохранены дамп БД и медиа вне checkout. Обновлённый дамп восстановлен в отдельную `afara_content_acceptance`, медиа скопированы в отдельный каталог; проверки выполняются против этой копии. Это локальная проверка восстановления и сохранности, а не настроенное шифрованное внешнее резервирование production.

Текущая Docker-сборка также проверена после доработки; в этой облачной VFS-среде для метаданных buildx использован `BUILDX_CONFIG=/workspace/.cache/afara-buildx` (стандартный домашний каталог доступен только на чтение). Подход не меняет сетевую политику и не отключает TLS. Прежние тестовые AFARA-образы сохранены перед освобождением устаревшего кеша; volumes PostgreSQL/media не очищались. На обычном хостинге этот override не обязателен.

## Шаблон услуг, 16.10.2026

Миграция `20261016_120000_service_pages` добавляет значение `service` к типу страницы и её версии. Полная цепочка из пяти миграций проверена на пустой `afara_services_acceptance`. Для существующей development-базы с legacy schema-push использован отдельный узкий `AFARA_DB_PUSH=false npm run db:service-pages`; он не запускает начальные миграции, не переписывает страницы и регистрирует только эту добавку. Это не преобразует прежнюю историю schema-push в production-baseline. Перед переносом такой базы требуется отдельная проверка истории и схемы.

Содержательное обновление применяется отдельно после резервного копирования: `AFARA_DB_PUSH=false AFARA_EXPANSION_BASELINE=/приватный/снимок.json npm run content:expand` для плана; `-- --apply` — для явно согласованной публикации. Исходный снимок включает pages, site, draft и knowledge; его нельзя хранить в публичном репозитории. Повторное применение проверено без дубликатов; изменённые владельцем записи и черновики пропускаются. Файлы шести иллюстраций сверяются с SHA-256 манифеста до записи.

## Готовность к переносу, 18.10.2026

Данные существующей CMS обновлены, 74 ответа опубликованы, исходные страницы и медиа сохранены. Legacy-база проверена на полное совпадение со свежей схемой шести миграций; baseline принят с записью аудита, повторный штатный `db:migrate` проходит без изменений. Независимая копия восстановлена до обновления; актуальные данные готовятся к отдельному приватному переносу.

Docker-образ объединяет production-зависимости, сервер, worker и CLI; дублирующий слой standalone node_modules убран. Eager SMTP verify отключён: недоступная почта не блокирует запуск страниц и readiness. Реальная отправка остаётся в постоянной очереди с TLS, ограниченными тайм-аутами и повторами. Проверены production-HTTP, закрытые API/MFA без допуска, idempotency и доставка через авторизованный STARTTLS к изолированному Mailpit. Реальный SMTP-провайдер и MFA-шлюз требуют параметров оператора.

Пошаговый перенос, адреса, восстановление базы/медиа и проверки домена — [HOSTING_HANDOFF.md](docs/HOSTING_HANDOFF.md); актуальные проверки — [отчёт](docs/RELEASE_QA_2026-10-18.md).
