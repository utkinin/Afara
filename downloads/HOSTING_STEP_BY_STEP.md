# AFARA · запуск на своём домене

Комплект от 21.10.2026. Сначала можно смотреть [публичный сайт](https://utkinin.github.io/Afara/). Для админки и серверных функций нужен отдельный хостинг.

## 1. Что заказать

Рекомендуемый вариант — VPS с Ubuntu 24.04 LTS, Docker Engine и Compose v2: от 2 CPU, 4 GB RAM, 40 GB SSD. Для сборки оставлять хотя бы 10 GB свободными. Выберите регион хранения с учётом фактических требований к персональным данным и доступности ваших сервисов. Обычный тариф только для PHP или статических файлов не подойдёт.

Домен, сервер и почтовый сервис оформляются на владельца AFARA. Включите MFA в аккаунтах. Не требуется покупать отдельный домен для коротких ссылок. Стоимость зависит от выбранного поставщика; ничего автоматически не приобретается.

## 2. Из чего состоит перенос

| Файл/часть | Для чего | Как хранить |
| --- | --- | --- |
| `AFARA_Hosting_2026-10-21.zip` | Полный отслеживаемый код, Docker, инструкция, шаблоны настроек | Можно скачать из публичного превью |
| `AFARA_CMS_Transfer_2026-10-21.tar.gz` | Наполненная база и все сохранённые файлы media | Только приватно: защищённая загрузка на сервер/SFTP |
| `.env.production` | Новые пароли, домен, SMTP, MFA и при необходимости ключ модели | Только на сервере или в secret store, права 0600 |

В публичном ZIP **нет базы владельца, заявок, паролей и `.env.local`**. Он содержит также исторические документы; начинать следует с этой инструкции. Список файлов и SHA-256 находятся в ZIP. Приватный архив не кладётся в GitHub, webroot или папку downloads. Без него сайт запустится без текущего наполнения — повторный seed эту задачу не решает.

## 3. Что достаточно сообщить мне для продолжения

После выбора хостинга: название провайдера, домен, IP/имя сервера и доступный способ подключения. Это не секреты. Для управления добавьте отдельного участника в проект провайдера либо отдельного SSH-пользователя с персональным публичным ключом; конкретный ключ подготовим при подключении. Проверьте отпечаток сервера в панели провайдера. Доступ должен быть отзываемым; административные права предоставляются только для нужных операций. Членство в группе Docker фактически даёт права уровня root.

Пароль root, приватный SSH-ключ, пароль админки, SMTP и ключи API в чат не присылайте. Их вносят через защищённые настройки подключённой среды/секретов либо непосредственно на сервере. Можно предоставить доступ через интеграцию провайдера, если она будет доступна. Учётные записи и резервные способы входа остаются у владельца.

После подключения я смогу выполнять обновления в рамках доступной среды. Постоянную работу сайта обеспечат сервер и Docker; текущая сессия Codex не заменяет мониторинг и обслуживание. Публикация будущих правок CMS будет сразу менять серверный сайт; GitHub Pages обновляется отдельным статическим экспортом.

## 4. Подготовка сервера

Установите Docker Engine/Compose по [официальной инструкции Ubuntu](https://docs.docker.com/engine/install/ubuntu/) и Caddy по [официальной инструкции](https://caddyserver.com/docs/install#debian-ubuntu-raspbian). Откройте 80/443 для web и ограничьте SSH согласно своему способу доступа. База не должна иметь публичного порта. Не используйте development `compose.yaml` на публичном сервере.

Распакуйте публичный ZIP в домашний каталог пользователя развёртывания. Перейдите в его `project/`. Все следующие команды выполняются **из этого каталога**, не из папки HTML-превью. Приватный архив разместите отдельно, например в `$HOME/afara-private` (права каталога 0700, файлов 0600):

```bash
umask 077
mkdir -p "$HOME/afara-private"
chmod 700 "$HOME/afara-private"
tar -xzf "$HOME/afara-private/AFARA_CMS_Transfer_2026-10-21.tar.gz" -C "$HOME/afara-private"
(cd "$HOME/afara-private" && sha256sum -c SHA256SUMS)
cp deploy/production.env.example .env.production
chmod 600 .env.production
```

Проверка архива должна завершиться `OK`. Заполните файл приватным редактором. Для `POSTGRES_PASSWORD` и `PAYLOAD_SECRET` отдельно сгенерируйте случайные значения `openssl rand -hex 32`; не публикуйте вывод. В `DATABASE_URL` вставьте тот же пароль БД. Если пароль не hex, специальные символы в URL нужно кодировать. Не заменяйте существующий PAYLOAD_SECRET при обычном последующем обновлении.

Обязательные адреса — `APP_URL` и `AFARA_PUBLIC_URL`, оба `https://ваш-домен`, **без `/Afara`** и без пути. Заполните рабочий SMTP (587 STARTTLS или 465 TLS), адрес отправителя и реквизиты Cloudflare Access. `AFARA_DB_PUSH=false` сохраняется. Ключ модели необязателен: поиск по утверждённой базе работает без него.

Удобная функция для всех следующих команд (в новой SSH-сессии объявить снова):

```bash
dc() { docker compose --env-file .env.production -f compose.production.yaml "$@"; }
dc config --quiet
docker build -t afara:local .
dc up -d --wait db
```

Не печатайте `dc config` без `--quiet`: вывод содержит секреты. Ошибка проверки TLS/npm во время сборки требует исправления доверенных сертификатов/сети; отключать проверку не нужно.

## 5. Восстановление текущего CMS

Этот раздел — **для первой установки в пустую БД и пустой media-volume**. Если сервер уже содержит AFARA, не выполнять его повторно: см. раздел обновления ниже.

```bash
dc exec -T db psql -U afara -d afara -Atc "select count(*) from pg_tables where schemaname='public';"
```

Результат должен быть `0`. При другом результате остановите перенос и сохраните имеющиеся данные. Наполненный dump уже содержит схему: запуск начальных миграций перед восстановлением не требуется.

```bash
dc exec -T db pg_restore -U afara -d afara --no-owner --no-privileges --exit-on-error < "$HOME/afara-private/database.dump"
dc run --rm --no-deps --user root -T web sh -c 'test -z "$(ls -A /app/media)" && tar -xzf - -C /app/media --strip-components=1 --no-same-owner && chown -R node:node /app/media' < "$HOME/afara-private/media.tar.gz"
dc run --rm -e AFARA_STAGE=build web npm run db:migrate
```

У CLI миграций временно указан `build`; web и worker остаются в production. Ни seed, ни `--clean`, ни автоматический schema push не нужны. Сверьте счётчики с приватным `transfer-manifest.json`:

```bash
dc exec -T db psql -U afara -d afara -Atc "select 'pages',count(*) from pages where _status='published' union all select 'knowledge',count(*) from knowledge where _status='published' union all select 'media',count(*) from media where _status='published';"
```

Релиз 21.10: 21 страница, 82 публичных ответа, 47 опубликованных медиа. Исторические версии и файлы тоже сохранены; их количество отличается от числа активных изображений.

Создайте владельца интерактивно (email должен совпадать с разрешённой учётной записью MFA). Пароль вводится скрыто:

```bash
dc run --rm web npm run create:admin
dc up -d web worker
curl -fsS http://127.0.0.1:3000/api/health
```

В исходной базе пользователей нет. Если при переносе появятся реальные пользователи, команда откажется создавать второго владельца — их нужно сохранить.

## 6. Домен, HTTPS и доступ к админке

1. Направьте DNS домена на сервер. Если используете Cloudflare Access, подключите домен к Cloudflare и включите проксирование нужной записи.
2. В `deploy/Caddyfile.example` замените `afara.example.com` своим доменом. Установите содержимое в `/etc/caddy/Caddyfile` с учётом уже обслуживаемых сайтов. Проверьте `sudo caddy validate --config /etc/caddy/Caddyfile` и только затем `sudo systemctl reload caddy`. Caddy получает и продлевает сертификат при доступном DNS/80/443. В Cloudflare выберите **Full (strict)**.
3. Настройте self-hosted приложение Cloudflare Access с защищёнными путями `/admin*`, `/preview*`, `/api/*`. Для этих путей нужен **один и тот же AUD**: используйте несколько public-hostname/path назначений одного приложения. Policy Allow — только назначенным сотрудникам через IdP, который обязательно запрашивает MFA. Не используйте только email-OTP как замену независимому второму фактору. Разные независимые приложения с разными AUD не подходят к текущей настройке сервера.
4. Более специфичные приложения Bypass нужны только для публичных API: `/api/inquiry`, `/api/consultant`, `/api/health`, `/api/media/file/*`, `/api/analytics/track`, `/api/analytics/consent`. Обычные публичные страницы и `/_next/*` остаются вне защищённых путей. Проверьте приоритет исключений по текущему интерфейсу Cloudflare. Никогда не создавайте общий Bypass `/api/*`. Если ваш тариф/панель не позволяет собрать назначения с одной аудиторией, сначала согласуйте эквивалентную схему доступа; не отключайте серверную проверку.
5. Установите `ACCESS_TEAM_DOMAIN=имя-команды.cloudflareaccess.com`, `ACCESS_AUDIENCE` из приложения и выполните `dc up -d --force-recreate web worker`. Проверка токена на сервере остаётся обязательной: поддельный заголовок не заменяет подпись, а email токена должен совпадать с email пользователя CMS.

Схема правил Cloudflare выше — перечень необходимых публичных исключений и защищённых путей, а не автоматически настроенная интеграция. При необходимости специалист настраивает эквивалент через Cloudflare Tunnel; нельзя открыть всю `/api/*` как Bypass. Проверьте доступ через домен и прямой IP: без MFA админка и закрытые API не должны открываться. Ограничьте origin по актуальным IP Cloudflare/туннелю, сохранив канал администрирования и выпуск TLS. Не включайте доверие аналитики к заголовкам Cloudflare, пока origin доступен в обход шлюза. Не кешируйте `/admin*`, `/api/*`, `/preview*` или `/s/*` на CDN.

## 7. Что заполнить перед приёмом клиентов

В CMS `/admin`: опубликованные контакты и реквизиты оператора; настоящие privacy/consent документы; в закрытом разделе «Уведомления» — реальный email получателя. Для аналитики нужны также документ analytics, согласие посетителя и отдельное включение в Site. Пустые поля не заполнялись вымышленными данными. Реальные работы, портрет специалиста и отзывы добавляются после предоставления материалов и прав.

Настройки SMTP находятся на сервере, получатель уведомлений — в CMS. Это две разные настройки. Приём заявок и аналитика до юридического наполнения намеренно ограничены. Для расширенных ответов модели отдельно согласуйте передачу сообщений провайдеру, задайте ключ и включение; без него консультант ищет публичные материалы и даёт ссылки.

## 8. Приёмка на реальном домене

- Главная, партнёры/white label, пошив по размерам, уход, яхты и все направления: разные изображения, география Россия/ОАЭ, высоты 3–6 м, 360 px и масштаб 200%.
- Публикация тестового черновика: гость не видит черновик; после публикации видит обновление. ADMIN публикует; EDITOR не получает чужие полномочия. Сохранение и перезапуск контейнеров не теряют медиа/текст.
- Консультант: известный вопрос даёт ссылку на опубликованный источник, неизвестная цена/закрытые сведения — отказ. Новое опубликованное знание учитывается; снятое с публикации — исключается.
- Короткая ссылка `/s/имя`: 302 на опубликованную внутреннюю страницу; после отключения 404. Внешний сайт/черновик не допускается.
- После юридического наполнения: одна согласованная тестовая заявка сохраняется в CMS, повтор не дублирует её, реальный SMTP доставляет уведомление. Ошибка почты не теряет заявку, worker повторяет отправку.
- Без согласия нет аналитического сбора; отказ/удаление работают; отчёт виден только ADMIN. Проверить настройки DNT/GPC.
- Canonical/sitemap/robots и QR указывают на новый домен. Production индексируется по настройкам, GitHub Pages остаётся noindex-превью.
- Контроль состояния: `dc ps`, `dc logs --tail=80 web worker`; логи перед передачей очищаются от персональных данных. Реальные домен/SMTP/MFA проверяются после подключения, а не считаются настроенными по наличию файлов.

## 9. Резервные копии и следующие обновления

После начала работы единственный актуальный источник контента — CMS на вашем сервере. Старый переносной архив поверх неё не восстанавливать. Перед обновлением сохраните БД, media и защищённую копию конфигурации; для согласованной финальной копии кратко остановите web/worker и запретите редактирование. PostgreSQL оставьте включённым:

```bash
umask 077
afara_backup_dir="$HOME/afara-private/backup-$(date -u +%Y%m%dT%H%M%SZ)"
mkdir -m 700 "$afara_backup_dir"
dc stop web worker
dc exec -T db pg_dump -U afara -d afara -Fc > "$afara_backup_dir/database.dump"
dc run --rm --no-deps -T web tar -czf - -C /app media > "$afara_backup_dir/media.tar.gz"
dc up -d web worker
```

Если копирование завершилось ошибкой, сначала обеспечьте повторный запуск web/worker и диагностируйте ошибку; повреждённую копию не помечать успешной. Для регулярных копий используйте расписание, внешний зашифрованный storage и контроль результата; не храните единственную копию на этом же VPS. Проверяйте восстановление отдельно. Секреты не передаются через публичные архивы.

Далее получите проверенную версию кода, сохраните прежний Docker-образ отдельным тегом, соберите новый, в окне обслуживания выполните `dc run --rm -e AFARA_STAGE=build web npm run db:migrate` и пересоздайте web/worker. Базу и media-volume сохраняйте. Откат схемы не автоматизируется: некоторые миграции намеренно запрещают удаление данных. Не выполняйте `docker compose down -v`, `docker volume prune` или seed на рабочем сервере.

Технические подробности — [HOSTING_HANDOFF.md](https://github.com/utkinin/Afara/blob/main/docs/HOSTING_HANDOFF.md); отчёт текущего комплекта — [RELEASE_QA_2026-10-21.md](https://github.com/utkinin/Afara/blob/main/docs/RELEASE_QA_2026-10-21.md). Все команды первой установки нужно выполнять последовательно; хостинг и внешний MFA ещё не подключены.
