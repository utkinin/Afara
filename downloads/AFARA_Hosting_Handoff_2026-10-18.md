# Перенос AFARA на хостинг

Подготовлено 18.10.2026. Репозиторий main содержит сервер Next.js, Payload CMS, PostgreSQL, worker, публичные блоки и аналитику админки. GitHub Pages остаётся отдельным статическим просмотром. Домен/хостинг пока не подключены и услуги не приобретены.

## Что переносится

- Код — из main, с lockfile и Dockerfile. Node 24, PostgreSQL 17; образ работает пользователем node.
- Отдельно и приватно — актуальный custom-format dump PostgreSQL и архив каталога media. В них сохранено наполнение CMS; код и публичное превью не заменяют базу данных.
- Секреты задаются на новом сервере через защищённый env-файл/secret store. Не переносить их через публичный GitHub, чат или статический downloads.

Текущая база приведена к проверенной истории шести миграций. Перед принятием baseline сверены 568 колонок, 84 значения enum, 239 индексов и 115 ограничений со свежей базой, созданной полными миграциями. Тексты и медиа при этом не сбрасывались. Обычный `db:migrate` после восстановления не должен повторять начальные миграции.

## Параметры сервера

Для сборки на VPS разумная отправная точка — 2 CPU, 4 GB RAM и диск от 40 GB. До сборки оставить не менее 10 GB свободно и следить за местом отдельно от работоспособности приложения. В этой облачной среде Docker использует VFS, поэтому число слоёв особенно влияет на расход диска; на обычном overlay2 расход отличается. Worker и PostgreSQL должны работать постоянно, данные — на постоянных volumes.

Публично открывается HTTPS reverse proxy (например Caddy/Nginx). `compose.production.yaml` публикует web только на 127.0.0.1:3000; PostgreSQL не имеет внешнего порта. TLS и DNS проверяются после выбора домена. Не публиковать development compose с trust-аутентификацией.

## Секреты и адреса

Защищённый `.env.production` вне Git, права 0600:

- `POSTGRES_PASSWORD` — уникальный пароль БД; `DATABASE_URL` — пользователь afara, host db, база afara. Спецсимволы пароля URL-encode.
- `PAYLOAD_SECRET` — случайный секрет длиной не менее 32 символов. Не подставлять демонстрационное значение.
- `APP_URL=https://ваш-домен` и `AFARA_PUBLIC_URL=https://ваш-домен`, без `/Afara`. Второй адрес используется, в частности, в QR/контактных ссылках; GitHub Pages-адрес не должен остаться в production.
- `AFARA_STAGE=production`, `AFARA_DB_PUSH=false`, `MEDIA_DIR=/app/media`.
- Реальные `SMTP_HOST/PORT/FROM/USER/PASSWORD`; в закрытом разделе CMS «Уведомления» указать действующего получателя вместо тестового адреса. Production требует TLS и проверку сертификата. Временная недоступность почты не блокирует запуск страниц; уведомления остаются в outbox и повторяются worker.
- `ACCESS_TEAM_DOMAIN` и `ACCESS_AUDIENCE` — действующий MFA-шлюз Cloudflare Access/IdP с персональными доступами. Без него production-админка закрыта. Проверить, что origin нельзя обойти.
- Необязательные `AFARA_AI_ENABLED` и `AFARA_AI_API_KEY` включают провайдера консультанта отдельно. Без них работает поиск утверждённых материалов со ссылками. Секреты никогда не имеют префикса NEXT_PUBLIC.

Юридические сведения и документы ещё не предоставлены. Их нужно заполнить перед приёмом реальных заявок и включением аналитики. Публикация кода не заменяет эти сведения; вымышленные документы не создавались.

## Восстановление на новом пустом сервере

Команды выполнять в checkout, где лежат compose-файлы. В примерах `/private/...` — фактические приватные пути оператора, не публичные ссылки.

1. Сохранить `.env.production`, собрать образ `afara:local` штатным `docker build -t afara:local .`. В этой облачной машине для доверенного proxy CA использовался BuildKit secret `proxy_ca`; на обычном сервере он не нужен. TLS/проверку npm integrity не отключать.
2. Поднять только БД:

```bash
docker compose --env-file .env.production -f compose.production.yaml up -d --wait db
```

3. В **пустую** БД восстановить уже наполненный dump, без владельцев/привилегий прежней машины:

```bash
docker compose --env-file .env.production -f compose.production.yaml exec -T db pg_restore -U afara -d afara --no-owner --no-privileges --exit-on-error < /private/database.dump
```

Не запускать сначала исходные миграции в этой базе: dump уже содержит схему. Не использовать `--clean` поверх существующей базы. Если на хостинге уже есть данные, сначала отдельный backup и план обновления.

4. В новый пустой media-volume восстановить архив с верхним каталогом `media/`:

```bash
docker compose --env-file .env.production -f compose.production.yaml run --rm --no-deps --user root -T web sh -c 'tar -xzf - -C /app/media --strip-components=1 --no-same-owner && chown -R node:node /app/media' < /private/media.tar.gz
```

5. Проверить миграции отдельной командой, без запуска HTTP-сервера:

```bash
docker compose --env-file .env.production -f compose.production.yaml run --rm -e AFARA_STAGE=build web npm run db:migrate
```

`build` здесь относится только к короткоживущему CLI-контейнеру; web/worker из compose остаются production. Seed/reset/schema push для переноса не нужны.

6. Создать владельца приватно интерактивной `npm run create:admin` внутри `docker compose ... run --rm web`. Команда отказывается создавать второго владельца. Нет общего логина, пароля или опубликованной первичной регистрации. Затем запустить web и worker, настроить reverse proxy и DNS.

## Проверка после подключения домена

Открыть главную, партнёров, пошив по эскизам, контакты и все направления; проверить фотографии, мобильное меню, выбор задачи и блок ткани. Сверить canonical, sitemap, robots, QR и внутренние ссылки с новым доменом. Вход ADMIN/EDITOR, MFA и закрытые API проверить на реальном шлюзе.

После заполнения контактов и юридических документов отправить согласованную тестовую заявку, проверить запись в CMS и доставку через реальный SMTP; убедиться, что ошибка почты оставляет заявку сохранённой. Короткие ссылки должны давать 302 только на опубликованные внутренние страницы, а отключённые — 404. Консультант должен отвечать по опубликованной базе со ссылкой, неизвестное — отклонять.

Аналитика включается отдельно после публикации документов privacy/analytics и флага Site. Проверить отсутствие сбора до согласия, отказ, необязательную связь с заявкой, удаление истории и запрет доступа EDITOR/анониму. До включения пустой отчёт ожидаем и не означает поломку.

Настроить внешние резервные копии БД/медиа, контроль свободного места, readiness и наблюдение за worker. Проверить восстановление в отдельную БД. Хранить предыдущий образ; автоматический `migrate:down` аналитики намеренно запрещён, чтобы не удалить историю согласий.
