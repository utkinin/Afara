# Стандарт разработки проектов владельца AFARA

Редакция 22.10.2026. Это переносимая памятка решений и предпочтений из работы над AFARA. Применять по умолчанию в следующих проектах, если пользователь или требования конкретного проекта не говорят иначе. Факты бизнеса, доступы, стек и визуальные детали AFARA не становятся фактами другого проекта.

## 1. Как работать с владельцем

- Запрос «сделай», «обнови», «можешь?» означает выполнить работу и проверить результат. Не останавливаться на обещании, плане или инструкции, если действие доступно.
- Использовать уже принятые решения и выданные полномочия. Самостоятельно решать обычные обратимые вопросы реализации; не запрашивать повторно ответы из контекста, CMS или репозитория.
- Вопрос нужен, когда действительно отсутствуют существенные сведения или доступ. Пока ответ не получен, продолжать независимые части задачи. Молчание не подтверждает услуги, публикацию недостоверных фактов, покупки или доступ.
- После устранимой ошибки диагностировать причину, исправлять и продолжать. Не прекращать задачу из-за первой ошибки сборки, окружения или публикации.
- Кратко сообщать о существенных результатах и препятствиях. Итог: что реализовано, что проверено, какой адрес можно смотреть и что конкретно ещё требует материалов/настроек.
- Не обещать выполнение вне доступной сессии или автоматическое знание содержимого другой среды. Сохранять решения в файлах, которые прочитает следующий исполнитель.

## 2. Начинать с смысла проекта

До выбора компонентов определить: кто клиент, в какой ситуации обращается, какой результат получает, что входит в работу, как согласуется заказ и каков следующий шаг. Сначала проверить существующие материалы и подтверждённые факты.

Схема: **задача клиента → понятное решение → доказательства → процесс и границы → действие**. Она применяется к сайту, презентации, FAQ и консультанту. Сценарии — гипотезы для разговора, а не доказанные психотипы.

В B2B отдельно объяснять взаимодействие команд, исходные данные и ответственность. White label, NDA, брендирование, права на публикацию и общение с конечным клиентом описывать по подтверждённым условиям.

Структуру и семантику проектировать вместе: аудитории, направления, услуги, партнёры, работы, процесс, вопросы, контакты. Не смешивать тип помещения с видом услуги. Не создавать пустые страницы ради количества.

## 3. Выбирать достаточный способ запуска

| Задача | Вариант по умолчанию |
| --- | --- |
| Показать дизайн для согласования | Отдельное статическое noindex-превью с честным обозначением ограничений |
| Проверить спрос без хранения заявок | Лёгкий публичный сайт с подтверждённым способом связи; сообщение отправляет сам посетитель |
| Редактирование контента, заявки, роли, консультант, изменяемые ссылки | Сервер, CMS, постоянная БД/медиа и необходимые фоновые процессы |

Не переносить Next.js + Payload + PostgreSQL в каждый проект автоматически. Этот стек — проверенный вариант для задач AFARA; статическому запуску он может не требоваться. Покупки, выбранный тариф и внешний доступ не предполагать без основания.

Статический просмотр и работающий сервер — разные поставки. GitHub Pages не исполняет CMS, приватные API, сохранение заявок и серверные 302. Отчёт и интерфейс должны соответствовать выбранному режиму.

## 4. Дизайн, типографика и вёрстка

- При доработке сохранять согласованный визуальный характер и удачные решения. Существенный новый стиль не навязывать в задаче на исправления.
- Для нового проекта выбрать подходящие бренду палитру, шрифты и визуальную систему. AFARA использует спокойную интерьерную подачу, тёплые светлые фоны и сливовый акцент; это пример, не универсальный шаблон.
- Использовать токены цвета, типографики, ширин и отступов; общие компоненты и последовательную сетку. Избегать копий секций/меню и цепочек конфликтующих CSS-переопределений. Не менять старые стили вслепую без проверки итогового вида.
- Фотографии должны объяснять раздел. Для соседних направлений и карточек подбирать различающиеся содержательные изображения; не растягивать одну концепцию на весь сайт. Проверять разные кадрирования и реальные пропорции объектов.
- Hero свободно растёт с текстом. Не обрезать длинный русский заголовок фиксированной высотой, не уменьшать текст ради старого макета.

Проверенная стартовая шкала для подобного презентационного сайта; адаптировать к гарнитуре и задаче:

| Элемент | Телефон | Компьютер |
| --- | --- | --- |
| H1 | 42–48 px | 72–88 px |
| H2 | 34–40 px | 48–60 px |
| Заголовок карточки | 24–28 px | 28–34 px |
| Основной текст | 18 px | 20 px |
| Меню, кнопки, поля | 17–18 px | 17–18 px |
| Подписи | 15–16 px | 16 px |

Для основного текста ориентир line-height 1,55–1,65, длина строки 55–70 символов. У тонкой акцидентной гарнитуры проверить вес 500. Сначала повышать читаемость, затем оценивать необходимость смены семейства.

HTML: `header`, `nav`, `main`, `section`, `article`, `footer`; один основной H1 на обычную страницу, осмысленная последовательность заголовков. У полей видимые подписи, у изображений подходящий alt, декоративные элементы скрыты от озвучивания. Настоящие ссылки/кнопки вместо кликабельных div.

Клавиатура: видимый фокус, переход к содержимому, предсказуемое меню, Escape/возврат фокуса у модальных окон. Учитывать reduced motion, контраст и области нажатия около 44 px. Основной переход/контакт по возможности доступен без JavaScript.

## 5. Доверие и честный контент

Базовые блоки подбираются под проект: кто отвечает за работу; реальные кейсы; состав услуги; порядок согласования; факторы стоимости; контакты/география; короткие ответы на вопросы.

Кейс: **задача → особенности → решение → фотографии результата**. Имя специалиста, стаж, отзывы, сертификаты, выполненные работы, цены, сроки, свойства материалов и гарантии появляются только по подтверждению. Пустые факты не заменять убедительными выдумками.

Изображения-концепции и реальные работы различаются. Убрать навязчивое повторение служебных пометок допустимо, скрывать происхождение и выдавать иллюстрацию за опыт нельзя. Хранить основание прав и происхождение; промпты/документы и внутренние ограничения не обязаны публиковаться.

Описывать клиенту результат и сотрудничество. Внутренние расчёты, технологические карты, данные клиентов и бизнес-планы не публиковать по умолчанию.

## 6. Семантика, SEO и языки

- Делать отдельную карту: кластер → намерение → существующая или планируемая страница → основной смысл → FAQ/внутренние переходы. Встраивать ключи естественно в содержательный текст.
- Не дублировать близкие услуги ради ключей и не создавать тонкие геостраницы без собственного содержания. Частотности, исследования спроса и позиции не придумывать.
- Географию и условия каждого языка подтверждать отдельно. Не переводить локальные условия в обещание международной услуги. Не выводить переключатель/hreflang для отсутствующих переводов.
- Для боевого домена проверить title, description, canonical, Open Graph, sitemap, robots, 404 и префикс развёртывания. Тестовое превью закрывать от индексации; опубликованный клиентский сайт не оставлять случайно noindex.
- JSON-LD описывает видимые подтверждённые данные: подходящие Organization/WebSite/WebPage, Breadcrumb, Service и FAQPage. Не добавлять фиктивные Product/Offer/Review/AggregateRating. Микроразметка не гарантирует позиции, цитирование ИИ или расширенную выдачу; актуальные требования поисковиков проверять на дату запуска.

## 7. CMS и сохранение данных

- Добавление направлений, страниц, FAQ и пунктов навигации не должно требовать правки кода, если CMS входит в задачу. Ссылки вести на доступные опубликованные цели.
- Одна каноническая запись факта: контакты/география редактируются централизованно, а не расходятся в нескольких вручную заполненных FAQ.
- Разделять черновик, предварительный просмотр и публикацию; хранить версии и аудит. Права ADMIN/EDITOR и закрытые поля проверять на сервере, не только скрытием кнопок.
- **Не выполнять повторный seed/reset/schema push на наполненной базе.** Перед импортом/миграцией — приватный backup и проверка состояния. Импорт по умолчанию показывает план, создаёт только недостающие записи, сохраняет правки и черновики владельца.
- Применения должны учитывать повторный запуск, конкурирующие изменения и транзакции. Неизвестную изменённую запись сохранять и отдельно отмечать для проверки.
- Код не заменяет БД и файлы media. Сохранять историю и используемые файлы; не считать «лишним» всё, что не видно на текущей странице. Разрушительную чистку выполнять только после анализа ссылок/версий и отдельного основания.

## 8. Формы, взаимодействие и производительность

Минимальный первый шаг формы; контакты — когда понятна задача. Бюджет необязателен, если нет бизнес-причины требовать его. Выбор карточки переносит тему в существующий черновик, но не отправляет заявку и не затирает введённый текст. Возврат назад сохраняет поля.

Контактные данные отправляются только по явному действию. Не включать трекинг и пересылку персональных данных автоматически. Юридические сведения и согласия брать из реальных данных оператора.

Если есть серверная форма: серверная валидация, защита от спама, ограничение запросов, идемпотентность; заявка сохраняется независимо от временного сбоя почты. Worker и outbox повторяют уведомление, а не создают новую заявку.

Для статического старта разрешён прямой подтверждённый контакт. Подготовленный текст можно открыть в мессенджере; посетитель отправляет сам. Клик не считать полученной заявкой.

Основной экран не перегружать. Шрифты/изображения оптимизировать, подбирать responsive-варианты, дополнительный виджет загружать после открытия. Тяжёлый калькулятор, чат, автозапуск видео и анимации добавлять только при пользе для клиента. Следить за LCP/INP/CLS, весом и сдвигами макета; не заявлять метрики без измерения.

## 9. Консультант и короткие ссылки, если нужны проекту

Консультант получает только опубликованную одобренную базу сайта: услуги, FAQ, условия, разрешённые контакты/материалы. Черновики, заявки, служебные инструкции и личная библиотека недоступны. Ответ содержит действующие ссылки на источники. Неизвестные цены/сроки/свойства и закрытые запросы отклоняются. Изменение и снятие источника с публикации должно учитываться.

Начинать с простого подходящего поиска. Для AFARA работает PostgreSQL и выдача проверенных цитат, с необязательным модельным адаптером. Не строить сложную инфраструктуру без необходимости. Проверять известное/неизвестное, противоречия, попытки получить закрытое, изменение источников и сбой провайдера. Не обещать полностью исключить ошибки ИИ.

Управляемые короткие ссылки хранятся в БД: короткое имя, опубликованная внутренняя цель, включение/отключение, копирование/Share. Для изменяемой цели — серверный 302 без кеширования; выключенная/непубличная цель — 404. Не разрешать внешний open redirect, админку и документы клиентов. HTML-переход статического хостинга не называть 302.

## 10. Аналитика по наблюдаемым данным

Измерять полезное и минимально необходимое, включать по установленным требованиям и согласию. Не считать долю прокрутки прочтением, переход в Telegram заявкой, любой поиск нейропоиском, отсутствие referrer отсутствием влияния ИИ. Не собирать поля форм и контакты в события автоматически. Доступ к отчётам ограничивать; предусматривать удаление и срок хранения. Пустой отчёт при выключенном сборе — ожидаемый результат.

## 11. Проверки и публикация

1. Прочитать AGENTS.md, зафиксировать исходное состояние Git и нужную версию стека. Использовать существующий checkout. Сохранить незавершённые правки пользователя.
2. Выбрать проверки под изменение: сборка/типизация/линтер, существующие meaningful-тесты, реальные браузерные сценарии. Не создавать тесты, которые лишь повторяют реализацию. Ошибки разбирать, проверки не отключать ради зелёного статуса.
3. Мобильная вёрстка: минимум 360/390/768/1440 px, длинные заголовки и эффективный масштаб 200%; при необходимости 320 px. Нет горизонтального переполнения, сломанных фото, недоступного меню и потерянного ввода. Эмуляцию не выдавать за проверку физического телефона.
4. Для CMS/API отдельно проверить анонима, EDITOR, ADMIN, публикацию/отзыв, закрытые поля/медиа, консультанта, формы и redirects. Изменяющие тесты — только отдельные синтетические БД и media, не CMS владельца.
5. Сверить сохранность прежних записей и проверить восстановление backup. Имя процесса, открытый порт и HTTP 200 главной сами по себе не подтверждают работу остальных функций.
6. Опубликовать только подготовленный и проверенный артефакт, если публикация входит в выданные полномочия. Сохранить историю, не использовать force и не перезаписывать более свежие изменения.
7. Проверить успешный workflow/deploy для нужного commit, затем фактический обычный публичный адрес без обязательного cache-busting параметра. Проверить страницы, медиа, CSS/JS и загружаемые архивы; при необходимости сравнить SHA-256.
8. Версионировать изменяемые ресурсы по содержимому, исправлять причины устаревшего кеша. «Закоммичено» и «опубликовано» — разные статусы.

## 12. Перенос и дальнейшее управление

Передавать удобный комплект: понятная стартовая страница/README, пошаговые команды, версия/commit, контрольные суммы и отчёт проверок. Отдельно приватно передаются БД и media; секреты не входят в публичный архив.

Для серверного варианта: production-конфигурация, HTTPS reverse proxy, постоянные volumes, внутренний PostgreSQL, автоперезапуск web/worker, действующий SMTP, персональная защищённая админка, внешние backups и проверенное восстановление. Учесть свободный диск и особенности Docker; не удалять volumes ради успешной сборки.

Для статического варианта: готовый статический каталог, настройки настоящего хостинга, canonical/robots/404/redirects/headers, рабочий контакт и проверка лимитов тарифа/доступности. Исходники серверного проекта не выдавать за готовую статику.

Домен/хостинг принадлежат владельцу. Для управления использовать персонального участника или SSH-доступ с публичным ключом и возможностью отзыва. Приватные ключи и пароли не запрашивать в чате. Не менять DNS вслепую: сохранять действующие MX/TXT/почту и подтверждать права. Агенту не приписывать постоянный доступ после окончания сессии.

## Что считать завершением

Пользователь получает действующий адрес или конкретный проверенный артефакт, сохранённый контент и короткий отчёт. Ясно разделены **реализовано**, **действительно проверено**, **ещё нужны материалы/доступы/настройки**. Не писать «всё работает», пока существенный сценарий не проверен.
